DocMost: отчет по документации Insapp

Повторно проверены выгрузка DocMost, карта Public API и локальные кодовые базы ОСАГО, КАСКО и ипотеки. Результат ниже разделяет продуктовые сценарии, frontend, backend и реальные HTTP-контракты.

Результат анализа

Выгрузка DocMost и API-файлы проверены повторно

Что действительно покрыто DocMost

Сервисы и state machines, рантайм и DI, Public API, DataAccess, модели и БД, Quartz, интеграции и колбэки, ARM, безопасность, deploy, тесты, PII, наблюдаемость и инциденты. Это рабочий технический слой, а не пустая заготовка.

Что подтверждено кодом и API

Frontend ОСАГО, КАСКО и ипотеки подтверждает реальные маршруты, поля формы, request/response, polling и обработку ошибок. Backend-матрица подтверждает маршруты контроллеров, доступ и побочные действия.

Что исправлено в предлагаемой структуре

Продуктовые статьи описывают путь клиента. Frontend и backend получили отдельные страницы кода. HTTP API вынесен в 40.01.* с телами запросов, ответами, ошибками, повтором и ссылками на реализацию.

Актуальность материалов

В метаданных экспорта: 15 страниц обновлены в мае, 23 - в июне, 18 - в июле и 21 - в августе. Последние изменения 24.08.2026 затронули каталог сервисов, модель данных, ARM-endpoints и deploy/миграции.

P1

Две разные карты

У технической ветки нет одной понятной точки входа.

P1

Номер не является адресом

Внутри `20. Монолит и разработка` используются дочерние номера `10-80`.

P1

Описание системы смешано с работой над документацией

`80.*` содержит аудит, список пробелов и даты проверки рядом с техническими инструкциями.

P1

API был смешан с кодом frontend

Название Angular-метода не описывает HTTP-контракт. В новой структуре эти слои разведены между `20.03`, `20.04` и `40.01.*`.

P2

Повторяются смыслы `40` и `50`

Одни номера используются внутри монолита, другие - на уровне Insapp.

P2

Нет паспорта актуальности

На странице должны быть тип, дата проверки, owner, Git evidence и trigger обновления.

P2

Дублируются title и H1

Это ухудшает оглавление, поиск и чтение длинных веток.

Модель работы

DocMost - основная документация; Git - обязательный источник первого этапа
01

Git, Tracker, Wiki

Подтвержденные источники изменения. Git-кодовая база обязательна в первой волне проверки.

02

Hermes

Собирает нужные источники, исключает секреты и PII, находит страницы для обновления и создает черновик.

03

Человек: review

Сверяет API, порядок действий, ограничения и смысл изменения. При ошибке уточняет правила Hermes.

04

Человек: публикация

После согласования публикует через Hermes. Обновленная страница в DocMost становится основной версией.

Что писать в страницах

Обычный состав технической документации

На любой основной странице

  • Что описывает страница и для кого она нужна.
  • Кто отвечает за страницу.
  • Дата последней проверки.
  • Ссылки на Git, задачу, API и связанные страницы.
  • Когда страницу нужно пересмотреть.

Страница продукта

  • Путь клиента, экраны и условия перехода.
  • Статусы заявки и что видит клиент.
  • Поля формы, обязательность и проверки.
  • Офферы, документы и оплата как продуктовые шаги.
  • Ссылки на HTTP API и код без копии их содержания.

Страница HTTP API

  • Назначение, точный path и HTTP-метод.
  • Тип доступа и место передачи ключа.
  • Request и response с типами и примерами.
  • `result=false`, сетевые ошибки и конечные статусы.
  • Повтор, лимит, идемпотентность и побочные действия.

Страница интеграции

  • Кто с кем обменивается данными.
  • Порядок вызовов и колбэки.
  • Какие данные передаем и как их сопоставляем.
  • Ключи доступа, тестовый контур и контакт.
  • Повторная отправка, ошибки и проверка работы.

Страница frontend-кода

  • Приложение, маршрут, компонент и Angular-сервис.
  • Как собирается request из формы.
  • Состояние, кэш и восстановление заявки.
  • Polling, timeout и обработка `result=false`.
  • Ссылка на внешний контракт в `40.01.*`.

Страница backend-кода

  • Controller action, route, атрибуты и request DTO.
  • Сервисный слой, state machine и DataAccess.
  • Смена статуса, внешняя отправка или Quartz.
  • Логи, тесты и риск повторного вызова.
  • Ссылка на внешний контракт в `40.01.*`.

Инструкция по инциденту

  • Как понять, что случилась проблема.
  • На кого влияет проблема.
  • Где посмотреть логи и метрики.
  • Пошаговые действия для исправления.
  • Кому передать проблему и что записать после исправления.

Следующие шаги

Очередность внедрения

1. Утвердить одну карту

`00.01. Карта документации` становится единственной точкой входа. На старых страницах поставить ссылку на новый путь.

2. Разложить текущие страницы

Технические материалы из старой ветки `20` разнести по разделам `20`, `40`, `50` и `60`: код, партнеры, ARM и эксплуатация.

3. Добавить сведения о странице

На основной странице указать тип, дату проверки, owner, ссылку на Git и когда ее нужно обновить; затем проверить ссылки и убрать дубли в архив.
