# Вопросы для уточнения документации Insapp

## 1. Что является основной страницей

1. Какие страницы DocMost уже считаются основными и должны только связываться из нового дерева, без второго описания?
2. Какие текущие страницы устарели, служат архивом или должны быть заменены новыми продуктовым страницами?
3. Кто подтверждает, что новая страница стала основной: владелец продукта, backend, аналитик или руководитель направления?
4. Нужна ли отдельная страница владельцев разделов с именем команды и каналом для вопросов?

## 2. Продукты и партнеры

1. Какие продукты входят в первый релиз базы: ОСАГО, КАСКО, ипотека, МФО, FinProduct или другие?
2. Какие партнерские сборки нужно описывать отдельно, а какие отличаются только настройкой и должны оставаться в общей странице продукта?
3. Какие сценарии обязательны для каждого продукта: новый клиент, возврат к заявке, оффер, отказ, документы, оплата, офлайн и пролонгация?
4. Где проходит граница между страницей продукта, страницей страховой и страницей общего API?

## 3. API и данные

1. Для каких методов нужны полные контракты запроса и ответа, а для каких достаточно ссылки на технический DocMost?
2. Где хранится утвержденный список кодов ошибок и действий клиента по каждому методу?
3. Какие поля формы и ответа могут меняться у партнера, а какие одинаковы для всех сборок?
4. Какие статусы заявки, оффера, документа и оплаты считаются пользовательскими и должны быть описаны в продуктовой странице?
5. Нужна ли отдельная таблица соответствия: экран -> поле -> API -> backend-модель?

## 4. ARM и эксплуатация

1. В какой момент заявка должна переходить из онлайн-пути в ARM: нет оффера, ошибка документа, нет платежной ссылки, ручная продажа или другой случай?
2. Какие данные оператор обязан видеть и какие действия ему разрешены по продукту?
3. Какие инциденты требуют отдельной короткой инструкции для первой линии?
4. Какие логи, метрики и идентификаторы достаточно приложить к обращению, не передавая PII и секреты?
5. Кто владелец каждой инструкции по инциденту и как часто она проверяется?

## 5. Правила обновления

1. Какой источник важнее при расхождении: код, контракт партнера, задача, Wiki или DocMost?
2. Какие изменения обязаны запускать обновление документации: новый endpoint, поле, статус, партнерская настройка, экран, миграция или инцидент?
3. Где вести список страниц, которые требуют проверки после изменения кода?
4. Кто проверяет черновик Hermes и в какой срок?
5. Нужны ли дата проверки, владелец и ссылка на источник на каждой странице или только на ключевых?

## Что уже достаточно для первого слоя

- Текущая выгрузка DocMost подробно покрывает технический монолит.
- Локальные фронтовые API-файлы дают факты для ОСАГО, КАСКО и ипотеки.
- Первым слоем можно сделать продуктовые пути, методы API, поля, документы, оплату, границу ARM и инструкции по типовым сбоям.

## Что даст ответы на вопросы

- Одну основную страницу на каждую тему вместо дублей.
- Понятную границу между продуктом, API, backend, ARM и эксплуатацией.
- Документацию, которую можно обновлять по изменению кода, а не переписывать целиком.
